CONTINUE — ПРОТОКОЛ ПРОДОЛЖЕНИЯ ПРОЕКТА
=======================================

Этот файл — входная точка для любого агента (ИИ или человека), который
продолжает проект без знания всей его истории.

ПОРЯДОК ВХОДА (несколько минут)

1. README.txt — что это за проект.
2. CHARTER.txt — что нельзя нарушать.
3. ROADMAP.txt — текущий этап и следующий малый шаг (раздел «Где мы
   сейчас»).
4. registry/METHODS.txt (индекс) — найти нужную ветвь и исходник;
   карточки методов исходника — в registry/<ветвь>/<файл>.txt.
5. Спецификация слоя из SPEC/ — точный контракт слоёв, которых
   касается изменение.

ПРАВИЛА РАБОТЫ

- Не читать репозиторий целиком. Читать только карточки методов нужной
  ветви (registry/) и спецификацию её слоя.
- Одно изменение = одна ветвь (или пара «ветвь + её тест»).
- Изменение готовится в отдельной копии, проверяется инструментами
  (python tools/check_limits.py;
  python -m unittest discover -s tests -t . -v;
  python tools/registry_scan.py), затем передаётся человеку для
  применения через веб-интерфейс GitHub полными текстами файлов.
- После применения человек сообщает состояние CI (вкладка Actions).

ОБЯЗАННОСТИ КАЖДОГО ШАГА

- Оставить CI зелёным.
- Реестр методов CI обновляет сам: убедиться, что после шага появился
  коммит «ci: регенерация реестра методов» (или реестр не изменился).
- При изменении поведения — обновить спецификацию и тесты.
- При закрытии/начале этапа — обновить раздел «Где мы сейчас» и журнал
  этапов в ROADMAP.txt.
- Ни одного файла длиннее 500 строк.
- Ни одного файла .md: документация — только .txt (CHARTER.txt, п. 11).

ЕСЛИ ДОКУМЕНТЫ РАСХОДЯТСЯ

Истина в порядке убывания приоритета: спецификация слоя -> карточки
методов -> тесты -> остальная документация. Конфликт фиксируется
в пользу старшего источника, младший исправляется в том же шаге.

ФОРМАТ ОБМЕНА «ИИ <-> ЧЕЛОВЕК»

- ИИ выдаёт: список файлов (путь, действие: создать/заменить/точечно
  поправить) и полное содержимое каждого (для точечных правок — старую
  и новую строку).
- Человек копирует содержимое файлов только из код-блоков сообщения
  (кнопка копирования), никогда из отрендеренного вида.
- После вставки человек открывает файл на GitHub и сверяет его первую
  и последнюю строки с код-блоком: .txt не рендерится, поэтому для
  контроля достаточно совпадения начала и конца и отсутствия «съеденных»
  пустых строк.
- Человек применяет и отвечает состоянием CI плюс любые отклонения
  (например, сообщение об ошибке из Actions).
- Следующий шаг готовится только по фактически применённым изменениям.

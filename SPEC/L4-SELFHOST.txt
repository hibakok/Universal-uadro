SPEC L4 — SELFHOST v0.8: САМОХОСТИНГ №1
=======================================

Статус: v0.8 от 2026-11-06 — действующая основа Этапа 4 (ROADMAP.txt,
Этап 4; дизассемблер l2.uasm.disasm закрыт по v0.1, ассемблер
l2.uasm.assemble — целиком по v0.2-v0.7: подшаги 1-4 — по v0.2-v0.5,
подшаги 5-6 — по v0.6, подшаг 7 — по v0.7; контракт эмулятора —
раздел 5Б v0.8).
Изменения: только новыми версиями (v0.9, ...) с записью в разделе
«История версий»; реализация и тесты обновляются в том же шаге.
Нумерация разделов сохраняется (новые разделы — 5А, 5Б): ссылки из
ROADMAP.txt, журнала и исходников остаются точными.

1. НАЗНАЧЕНИЕ
-------------

Самохостинг №1 — перевод инструментов uadro с бустрапа (Python, слой
T0) на собственные языки: собственные инструменты пишутся на uBrick
(SPEC/L3-UBRICK.txt), собираются компилятором uBrick и исполняются
на UVM (SPEC/L0-UVM.txt).

Инструменты этапа: дизассемблер uAsm, ассемблер uAsm, эмулятор UVM.
Компилятор uBrick остаётся бустрапом до uLang (Этап 6): инструментам
Этапа 4 он не нужен — они фильтры stdin -> stdout (раздел 4).

2. ДВОЙНЫЕ ВОПЛОЩЕНИЯ
---------------------

Каждая подсистема этапа живёт в двух воплощениях:

- эталон — Python-ветвь t0.* (уже существует; источник истины
  поведения);
- собственное воплощение — ветвь l1.*/l2.* на uBrick (строит этот
  этап).

Правила:

- собственное воплощение сверяется с эталоном побайтово на золотых
  наборах (раздел 6); расхождение — ошибка собственного воплощения;
- эталон не удаляется и не меняет поведения, пока живы оба: он нужен
  новым собственным инструментам и тестам;
- эталон удаляется, только когда его подсистему заменяет собственная
  производящая инфраструктура (uLang, Этап 6) — не в Этапе 4.

3. ИНСТРУМЕНТЫ ЭТАПА
--------------------

ИНСТРУМЕНТ        СОБСТВЕННОЕ       ЭТАЛОН            ВХОД -> ВЫХОД
дизассемблер      l2.uasm.disasm    t0.uasm.disasm    образ -> текст
uAsm                                                  uAsm
ассемблер uAsm    l2.uasm.assemble  t0.uasm.assemble  текст uAsm ->
                                                      образ
эмулятор UVM      l1.uvm.*          t0.uvm.*          образ -> вывод
                                                     программы

Размещение:

- исходники собственных инструментов: src/l1/*.ubrk, src/l2/*.ubrk —
  подкаталог src/ равен слою воплощения;
- собственный инструмент может состоять из нескольких исходников
  (SPEC/L3-UBRICK.txt, v0.3): главный файл собирает остальные
  строками use; все файлы инструмента лежат в его каталоге
  src/l<слой>/ (контракт инструмента перечисляет файлы); номера
  строк ошибок компиляции — объединённого текста;
- тесты: tests/test_l1_<модуль>.py, tests/test_l2_<модуль>.py;
- аннотации исходников собственных языков — «; @ключ значение»
  (сканер реестра понимает их с этого этапа); каждое слово инструмента
  uBrick описывается карточкой «; @method имя ( эффект )» с полями
  @in/@out/@does/@depends (DOC/CONVENTIONS.txt).

Имена ветвей собственных воплощений: <слой>.<подсистема>.<модуль>
(DOC/ARCHITECTURE.txt, «Замечание о двойных воплощениях»): l2.uasm.* —
инструменты слоя ассемблера, l1.uvm.* — эмулятор.

4. ДОГОВОР ПОТОКОВ
------------------

Все собственные инструменты Этапа 4 — фильтры:

- вход: байты stdin; чтение SYS 0 байт за байтом до EOF (значение
  0xFFFFFFFFFFFFFFFF — SPEC/L0-UVM.txt, раздел 6);
- выход: байты stdout; запись SYS 1;
- новых устройств этап не вводит (шина устройств — Этап 5);
  stderr-устройства нет: диагностика ошибок пишется в stdout строкой,
  контракт которой задаёт сам инструмент; единственный новый номер
  SYS — 2, завершение с кодом со стека (SPEC/L0-UVM.txt v0.2,
  раздел 6), нужен эмулятору (раздел 5Б);
- инструменты потоковые: буфер входа целиком не требуется; lookahead
  читается тем же SYS 0;
- коды завершения: 0 — успех; 16 — ошибка входа по контракту
  инструмента (пользовательские коды >= 16 — SPEC/L0-UVM.txt,
  раздел 3); ловушки UVM 1-8 — ошибки самого инструмента (баг),
  тестами не допускаются (уточнение для эмулятора — раздел 5Б:
  ловушки гостя — данные, а не баг).

Исключение (v0.2): ассемблер l2.uasm.assemble читает stdin целиком
в буфер ОЗУ — ссылки вперёд требуют двух проходов по тексту; лимит
входа и раскладка буферов — контракт инструмента (раздел 5А).
Эмулятор l1.uvm.* читает stdin целиком тоже — образ гостя
загружается в его ОЗУ до начала исполнения (раздел 5Б).

5. КОНТРАКТ ДИЗАССЕМБЛЕРА (l2.uasm.disasm)
------------------------------------------

Исходник: src/l2/disasm.ubrk. Эталон: tools/uasm_disasm.py, disasm()
(SPEC/L2-UASM.txt, раздел 8). Команды:

    python tools/ubrick_cli.py compile src/l2/disasm.ubrk ОБРАЗ.uvm
    python tools/uvm_cli.py ОБРАЗ.uvm < ВХОД.uvm > ТЕКСТ.uasm

Поведение — побайтово disasm() эталона (SPEC/L2-UASM.txt, раздел 8):

- инструкции по одной на строку: «МНЕМОНИКА» или «МНЕМОНИКА
  значение»; значения — десятичные слова 0..2^64-1;
- останов декодирования: неизвестный опкод или EOF внутри поля imm64;
  с опкода останова до конца входа данные печатаются директивами DB —
  по восемь аргументов на строку (неполная последняя строка — короче);
- EOF на границе инструкции — директив DB нет; пустой вход — пустой
  вывод; код завершения 0; ошибок входа нет.

Потоковая модель (механика, не поведение): вход читается байт
за байтом по мере декодирования; imm64 — lookahead восемь байтов;
EOF внутри imm64 — останов с опкода: хвост DB — опкод и прочитанные
байты поля.

Архитектурные решения (обязательные для всех инструментов этапа):

- таблицы данных — text-строки записей фиксированной ширины; таблица
  мнемоник — шесть строк по диапазонам кодов: 0x00-0x07 (стек),
  0x10-0x13 (память), 0x20-0x2C (арифметика), 0x30-0x35 (сравнения),
  0x40-0x45 (переходы), 0x50 (система); запись — восемь байтов:
  мнемоника, дополненная нулями; адрес записи = база строки +
  (код - низ диапазона) * 8; печать — словом prints (до нуля);
- признак imm64 — слово сравнений, без таблицы: коды 0x01, 0x07,
  0x40-0x43, 0x45, 0x50;
- печать десятичного числа — рекурсивное слово: старшие разряды
  печатает рекурсивный вызов (частное от деления на 10), затем
  младший (остаток + '0').

Диапазоны таблицы мнемоник совпадают с таблицей опкодов
(SPEC/L0-UVM.txt, раздел 5): внутри диапазонов пустых кодов нет.

5А. КОНТРАКТ АССЕМБЛЕРА (l2.uasm.assemble)
------------------------------------------

Исходники: src/l2/assemble.ubrk — главный файл (слова main, проходов
и диагностики) — и его use-включения (SPEC/L3-UBRICK.txt, v0.3):
asmmem.ubrk (раскладка ОЗУ и буферы), asmwords.ubrk (строки и слова:
деление буфера на строки, чистка строки, первое слово, аргументы
парами), asmmnem.ubrk (таблица мнемоник и поиск кода по мнемонике),
asmlex.ubrk (литералы и имена), asmline.ubrk (разбор строки в
запись), asmsym.ubrk (таблица символов), asmcode.ubrk (кодирование
записей). Эталон — tools/uasm_assemble.py и его ветви
(SPEC/L2-UASM.txt, раздел 7). Команды:

    python tools/ubrick_cli.py compile src/l2/assemble.ubrk ОБРАЗ.uvm
    python tools/uvm_cli.py ОБРАЗ.uvm < ИСТОЧНИК.uasm > ОБРАЗ.uvm

Поведение — assemble(text) эталона байт в байт (SPEC/L2-UASM.txt,
раздел 7): два прохода, метки и константы, ссылки вперёд, директивы
DB/DW/DS/DZ, диапазоны литералов, оборачивание отрицательных по
модулю 2^64.

Вход-выход (дополнение к разделу 4):

- вход — текст uAsm читается целиком (KEY до EOF) в буфер источника;
  переполнение буфера — «вход слишком большой», код 16 (единственная
  диагностика без номера строки — возникает при чтении, до разбора
  строк);
- выход — образ целиком из буфера образа, код 0; при ошибке образ
  не выводится — только диагностическая строка, код 16;
- диагностическая строка — «uAsm: строка N: текст»; тексты ошибок —
  SPEC/L2-UASM.txt, раздел 7; N — номер строки буфера источника,
  начиная с 1 (строки делятся по LF, концевой CR снимается — как
  split_lines эталона).

Раскладка ОЗУ инструмента (адреса фиксированы, лимиты — часть
контракта; собственный образ инструмента загружается с адреса 0
и лежит ниже буферов):

БУФЕР      АДРЕС    ЁМКОСТЬ   НАЗНАЧЕНИЕ
источник   0x10000  512 КиБ   текст uAsm из stdin
образ      0x90000  64 КиБ    собираемый образ UVM
символы    0xA0000  320 КиБ   таблица символов: записи «значение
                              8 байтов LE + имя + байт 0»
аргументы  0xF0000  4 КиБ     пары (адрес, длина) аргументов DB/DW
                              одной строки — не более 256; пара —
                              16 байтов: адрес и длина, слова LE

Ошибки ёмкости (код 16): «вход слишком большой» (без номера строки),
«образ слишком большой», «таблица символов переполнена», «слишком
много аргументов» (с номером строки). Имя символа — не длиннее
63 байтов: длиннее при определении — «слишком длинное имя», при
использовании не найдётся — «неизвестное имя X».

Механика (обязательные решения по образцу раздела 5):

- таблица мнемоник — те же шесть text-строк по диапазонам кодов;
  поиск кода по мнемонике — сравнение слова исходника с записями
  строк (код = низ диапазона + номер записи);
- признак imm64 — слово сравнений (как hasimm раздела 5, asmmnem);
- печать десятичного номера строки — рекурсивное слово (как printu
  раздела 5);
- разбор строки — var-ячейки записи asmline.ubrk: rk — вид записи
  (1 метка, 2 константа, 3 инструкция, 4 DB, 5 DW, 6 DS, 7 DZ),
  rn — длина имени метки либо константы (адрес имени — wa), rv —
  значение константы по модулю 2^64, rc — код мнемоники; слово
  и операнд — клетки wa/wl и ra/rl, аргументы DB/DW — argc и буфер
  аргументов, длина литерала DS/DZ — sl. Порядок разбора — раздел 7
  SPEC/L2-UASM.txt (parse_line эталона); ошибки разбора строки — уже
  диагностика «uAsm: строка N: текст» и код 16 (fail/failx). Буфер
  аргументов заполняют только строки DB/DW: операнд инструкции
  и правая часть константы — текст ra/rl, не слова-аргументы (лимит
  256 пар к ним не относится);
- промежуточные листинги подшагов 2-5 (слова, записи, символы)
  удалены: с подшага 6 инструмент выводит только образ при успехе
  либо диагностическую строку при ошибке (раздел 4). Механика
  проходов: клетка ps главного файла выбирает шаг записи
  (0 — p1step, 1 — p2step), проход 2 повторно проходит строки
  (linestep) и кодирует записи в буфер образа (asmcode.ubrk:
  putbyte/putword с лимитом 64 КиБ, resval — значения операндов
  и аргументов, emitdb/emitdw/emitds/emitdz/emitinstr); значение
  операнда разрешается прежде байтов — порядок ошибок эталона
  encode_instr; вывод — imgout, байты [imgbase, vc).

Подшаги ветви (смежные подшаги можно объединять в одном шаге; каждый
шаг оставляет репозиторий работоспособным):

1) каркас и память: раскладка ОЗУ, чтение stdin в буфер источника,
   лимит входа; пустой вход — пустой вывод, код 0;
2) строки и слова: деление буфера на строки и счётчик строк, чистка
   строки (комментарий «;» вне кавычек, крайние пробелы), первое
   слово, слова аргументов в массив пар, таблица мнемоник и поиск
   кода по мнемонике;
3) литералы и имена: десятичный, шестнадцатеричный, двоичный,
   символьный разбор с контролем переполнения, минус и диапазон
   -2^63..2^64-1, имена, строковые литералы DS/DZ;
4) разбор строки в запись: метка, константа, инструкция, директивы
   данных — по порядку раздела 7 SPEC/L2-UASM.txt;
5) таблица символов и проход 1: запись и поиск имён, адреса записей,
   повторные определения, метка в конце текста;
6) проход 2 и вывод: кодирование записей в буфер образа (опкод,
   imm64 little-endian, DB, DW, DS/DZ с escape), вывод образа при
   успехе, ошибки значений (имена, диапазоны, байты DB);
7) диагностика и золотой набор: строки ошибок с номерами, код 16,
   золотой набор (раздел 6), сквозной прогон — закрытие ветви.

5Б. КОНТРАКТ ЭМУЛЯТОРА (l1.uvm.*)
---------------------------------

Исходники: src/l1/emu.ubrk — главный файл (чтение входа, цикл,
main) — и его use-включения (SPEC/L3-UBRICK.txt, v0.3): mem.ubrk
(раскладка ОЗУ, стеки и память гостя), dec.ubrk (декодер), tab.ubrk
(дерево диапазонов — таблица обработчиков) и opsstack.ubrk,
opsmem.ubrk, opsarith.ubrk, opscmp.ubrk, opsjump.ubrk, opssys.ubrk —
обработчики групп опкодов, по файлу на группу (как t0.uvm.ops).
Эталон — ветви t0.uvm.* (SPEC/L0-UVM.txt). Команды:

    python tools/ubrick_cli.py compile src/l1/emu.ubrk ОБРАЗ.uvm
    python tools/uvm_cli.py ОБРАЗ.uvm < ГОСТЬ.uvm > ВЫВОД

Поведение — исполнение эталона байт в байт (SPEC/L0-UVM.txt,
разделы 1-6) на машине гостя: вывод — байты SYS 1 гостя, код
завершения — imm HALT либо код ловушки гостя.

Машина гостя (эталон в золотых прогонах — те же размеры:
--ram 524288 --ds 256 --rs 64): ОЗУ 512 КиБ, байтовая адресация,
образ с адреса 0; DS — 256 слов, RS — 64 слова.

Вход-выход (дополнение к разделу 4):

- вход — образ гостя читается целиком (KEY до EOF) в его ОЗУ;
  длиннее 512 КиБ — ловушка 7 гостя до начала исполнения (как
  load_image эталона: образ больше ОЗУ): код 7, вывод пуст; ошибок
  входа с кодом 16 у инструмента нет;
- SYS 0 гостя всегда даёт признак конца ввода: stdin инструмента
  израсходован образом; эталон в золотых прогонах получает пустой
  stdin — поведение совпадает;
- код завершения инструмента — код завершения гостя: imm HALT
  по модулю 256 либо код ловушки 1-8; передаётся SYS 2 узла (слово
  STOP, SPEC/L3-UBRICK.txt, раздел 4.1). Ловушки гостя — данные
  и код завершения, а не баг инструмента; ловушки самого
  инструмента на узле — баг, тестами не допускаются.

Раскладка ОЗУ инструмента (адреса фиксированы, лимиты — часть
контракта; собственный образ инструмента загружается с адреса 0
и лежит ниже буферов, как у ассемблера — раздел 5А):

БУФЕР   АДРЕС    ЁМКОСТЬ   НАЗНАЧЕНИЕ
образ   0x10000  512 КиБ   ОЗУ гостя; образ с stdin — с адреса
                           гостя 0
стек DS 0x90000  256 слов  стек данных гостя, растёт вверх
стек RS 0x90800  64 слова  стек возвратов гостя, растёт вверх
клетки  0x90A00  128 байт  gpc — PC гостя; gdsp — слов в DS;
                           grsp — слов в RS

ОЗУ узла — не менее 0x90A80 (тесты запускают инструмент в 1 МиБ
по умолчанию). Снимки стеков гостя после остановки читаются из ОЗУ
узла по раскладке — тест-кирпич прогона с сохранением машины
(расширение t0.infra.tests, подшаг 1).

Механика (обязательные решения по образцу разделов 5 и 5А):

- чтение образа — собственные кирпичи keyok/storebyte: дубли
  кирпичей asmmem.ubrk — ветви изолированы (CHARTER.txt, п. 2);
- память гостя — через базу 0x10000: адрес гостя a -> 0x10000 + a;
  проверка по байтам (слово — восемь байтов, как load_word/
  store_word эталона), ловушка 7;
- стеки гостя — gpush/gpop/gpick (ловушки 2/3), rpush/rpop
  (ловушки 4/5), ёмкости из раскладки;
- декодер: код — байт по gpc (вне ОЗУ гостя — ловушка 7);
  принадлежность кода — шесть диапазонов раздела 5 SPEC/L0-UVM.txt
  (внутри диапазонов пустых кодов нет), неизвестный код — ловушка
  6; признак imm64 — слово сравнений (код hasimm раздела 5А);
  imm64 — восемь байтов LE по gpc+1; следующий адрес — gpc+1 либо
  gpc+9;
- таблица обработчиков — дерево вложенных IF по шести диапазонам,
  внутри — по коду; ветвь — CALL слова-обработчика;
- SYS-мост: SYS 0 — KEY на DS гостя; SYS 1 — gpop и EMIT; SYS 2 —
  STOP с кодом гостя; прочий номер — ловушка 8.

Подшаги ветви (смежные можно объединять; каждый шаг оставляет
репозиторий работоспособным):

1) каркас и память: раскладка, клетки, чтение stdin в образ гостя,
   лимит 512 КиБ — код 7; тест-кирпич прогона с сохранением машины;
   образ в ОЗУ узла — байт в байт;
2) декодер и остановка: код, диапазоны, imm64, следующий адрес,
   ловушки 6/7; обработчики NOP и HALT, заготовка дерева и цикл:
   несколько NOP и HALT imm — код imm;
3) стеки гостя: gpush/gpop/gpick, rpush/rpop, обработчики группы
   «стек»;
4) память гостя: доступ по байтам, обработчики группы «память»;
5) арифметика и сравнения: обработчики групп «арифметика»
   (ловушка 1) и «сравнения»;
6) переходы и SYS: JMP/JZ/JNZ/CALL/RET и SYS-мост (ловушка 8);
7) золотой набор и закрытие ветви: раздел 6, сквозной прогон
   настоящим процессом.

6. СВЕРКА С ЭТАЛОНОМ
--------------------

Собственное воплощение проходит золотой набор: для каждого входа
выход инструмента равен выводу эталона байт в байт, код завершения
равен коду эталона.

Золотой набор дизассемблера (пополняется ветвью):

- пустой вход;
- каждый опкод v0.1 отдельно: без imm — байт опкода; с imm — опкод
  и поле imm64 (значения 0, 1, 12345, 2^64-1);
- обрыв imm64: опкод с imm в конце входа и 0-7 байтов поля;
- хвост данных: неизвестный опкод (0x51, 0xFF) и данные после; длина
  хвоста кратна восьми, короче восьми и смешанная;
- смешанные программы: инструкции обоих видов, данные в конце;
- образы программ этапов 1-2: собранные src/*.uasm.

Раунд-трип: assemble(disasm(B)) == B для каждого золотого образа B —
пока собирает Python-эталон (собственный ассемблер — раздел 5А).

Золотой набор ассемблера (пополняется ветвью l2.uasm.assemble,
контракт — раздел 5А):

- каждый вид записи отдельно: все мнемоники; imm-опкоды со значениями
  0, 1, 12345, 2^64-1; DB/DW с литералами всех форм и именами;
  DS/DZ с escape; метки, константы, ссылки вперёд, метка в конце
  текста;
- программы этапов 1-2: src/hello.uasm, src/arith.uasm,
  src/nested_calls.uasm — образы байт в байт с эталонными образами
  Этапа 1;
- тексты дизассемблера: вывод эталона disasm на образах золотого
  набора дизассемблера (выше) — сборка равна исходному образу;
- ошибки входа: по одному тексту на каждый вид ошибки раздела 7
  SPEC/L2-UASM.txt и ошибки ёмкости раздела 5А — диагностическая
  строка и код 16 (кроме переполнения таблицы символов: квадратичный
  поиск делает прогон полного набора записей многократноминутным для
  эмулятора — ошибка закреплена контрактом раскладки и решением
  подшага 5, tests/test_l2_assemble_sym.py);
- пустой текст — пустой образ; вход сверх лимита — «вход слишком
  большой» без номера строки.

Золотой набор эмулятора (пополняется ветвью l1.uvm.*, контракт —
раздел 5Б; эталон — та же машина гостя с пустым stdin):

- каждый опкод v0.1 отдельно: программа с известным эффектом —
  вывод проверяется байтами, стек — снимком DS по раскладке
  раздела 5Б;
- ловушки 1-8 — по короткой программе на каждую; выход PC за ОЗУ —
  JMP за границу, а не NOP-горка;
- программы этапов 1-2: src/hello.uasm, src/arith.uasm,
  src/nested_calls.uasm — вывод, код завершения и стеки как
  у эталона;
- вход длиннее 512 КиБ — код 7, вывод пуст;
- исключение: пустой вход и NOP-горки до конца ОЗУ — сотни тысяч
  гостевых инструкций, минуты на эмуляторе; ловушка 7 на границе
  ОЗУ покрывается JMP за границу (выше).

Прогоны: без процесса (подмена stdin/stdout — кирпич тест-набора)
и сквозной настоящий процесс с входным файлом (subprocess).

7. ПОРЯДОК ВЕТВЕЙ ЭТАПА
-----------------------

1. t0.infra.registry — сканер реестра понимает «; @»-аннотации
   исходников .uasm/.ubrk; интеграционные исходники src/ получают
   шапки и входят в реестр (закрывается вместе с принятием
   спецификации).
2. t0.infra.tests — кирпич run_with_io: прогон образа с подменёнными
   stdin/stdout (без процесса) для тестов собственных инструментов.
3. l2.uasm.disasm — дизассемблер на uBrick; подшаги: каркас и таблица
   мнемоник; imm64 и печать десятичного; хвост DB; золотые тесты
   и сквозной прогон.
4. l2.uasm.assemble — ассемблер на uBrick; контракт — раздел 5А
   (v0.2); подшаги: каркас и память; строки и слова; литералы
   и имена; разбор строки в запись; таблица символов и проход 1;
   кодирование и проход 2; диагностика и золотой набор.
5. l1.uvm.* — эмулятор UVM на uBrick; контракт — раздел 5Б (v0.8):
   подшаги: каркас и память; декодер и остановка; стеки; память;
   арифметика и сравнения; переходы и SYS; золотой набор.
6. l2.selfhost — связка: собственный ассемблер собирает, собственный
   эмулятор исполняет, собственный дизассемблер печатает; раунд-трип
   целиком на собственных инструментах; закрытие этапа.

Ветви 4-5 делятся на подшаги отдельными шагами (как ветвь 3); каждый
шаг оставляет репозиторий работоспособным и CI зелёным.

8. КРИТЕРИИ ЗАКРЫТИЯ ЭТАПА (DoD)
--------------------------------

- Дизассемблер l2.uasm.disasm: золотой набор проходит побайтово;
  раунд-трип на собственном выводе; сквозной прогон настоящим
  процессом — зелёные.
- Ассемблер l2.uasm.assemble: золотой набор текстов (включая ошибки
  входа: диагностика и код 16) собирается байт в байт с эталоном.
- Эмулятор l1.uvm.*: золотой набор программ исполняется с теми же
  выводом, стеками и кодами завершения, что у эталона.
- Связка l2.selfhost: раунд-трип «текст -> образ (собственный
  ассемблер) -> исполнение (собственный эмулятор) -> текст
  (собственный дизассемблер) -> образ» сходится без Python-инструментов
  (Python остаётся компилятором uBrick и тест-харнессом).
- CI зелёный; реестр методов охватывает новые ветви; ROADMAP.txt
  отражает закрытие этапа.
